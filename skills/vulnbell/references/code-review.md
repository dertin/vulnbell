# Static security review of the codebase

Run this workflow only when the user requests a review of their own code. It is separate from dependency advisory impact and does not execute the monitored code.

1. Establish scope from the current monitor snapshot: codebases, revisions, intended entry points, inputs, trust boundaries and files or languages that cannot be inspected. For each codebase, use `vulnbell schema code-review` and `vulnbell tools code-review --project <profile> --from <json>` to record `in_progress` before investigation, then save concise progress and unresolved gaps as you work. For each update, set `previous_revision` to the latest review's `revision` from the CLI or report JSON; on a conflict reload progress before continuing. Use `gaps` for unreviewed scope and `uncertainties` for unanswered reachability or context questions within reviewed scope. Record `partial` with its gaps when interrupted; record `complete` only after the stated scope was reviewed and no material gap remains. Completion requires a current CodeGraph index and does not imply exhaustive coverage. Do not infer deployment from source. Exclude private files, dependency trees and build output; inspect project-owned configuration separately.
   If the visible source changes during a review, start a new `in_progress` review with empty scope, gaps and uncertainties, and the last recorded `previous_revision`. Reassess prior conclusions against the new source.
2. CodeGraph is required for this review. Check `vulnbell doctor --json` and `codegraph status --json <codebase>`. If CodeGraph is missing or fails, in an interactive session ask the user to install or repair it using its [official instructions](https://github.com/colbymchenry/codegraph#get-started). Do not silently install it. For a missing index, run `codegraph init <codebase>` when the user has authorized initialization and the host and repository instructions permit it; otherwise request authorization in interactive sessions. Never initialize an index where repository instructions prohibit it. If unavailable, prohibited or not authorized, record the coverage gap; scheduled runs must have the tool and a current index prepared in advance. Continue independent dependency work, but do not claim the independent code review was completed. Use a current index for navigation in languages it covers. Its symbol and call relationships are leads: inspect actual source and do not infer complete coverage, runtime dispatch or reachability from an edge or a missing result. Record missing languages and bounded searches as limitations. Restricted runners can use `codebase_symbols` to locate indexed symbols within the permitted scope, then `codebase_read` to examine the source; this lookup does not initiate an independent codebase review.
3. Work in small units around public entry points and sensitive operations. Trace how input or state reaches the operation, the conditions under which it runs, and checks, error paths and callers that may prevent or alter the outcome. Follow only relevant relationships; report unresolved hops rather than expanding without a concrete question. Keep local and test configurations in scope, labelled by context.
4. For each candidate, independently challenge its mechanism: identify what must be controlled, which boundary can be crossed, the security consequence, and concrete evidence for and against it. Verify the language, framework, build target and enabled configuration where they matter. A missing graph edge, unsupported format or unseen caller does not establish safety. Record a supported problem as actionable, leave an unresolved material hypothesis in review, and do not describe an unproven condition as fact.
5. Register each assessed finding before moving to the next using `vulnbell schema code-finding` and `vulnbell tools code-finding --project <profile> --from <json>`. Set `review_revision` to the active review revision for the finding and for each supporting location; review every cited codebase first. Include the SHA-256 of each inspected line, without its line ending, as `line_sha256`; the restricted `codebase_read` and `codebase_search` tools provide these hashes. For reassessment or a moved finding, supply its existing `finding_id`, with a current location supporting the updated conclusion. If its former file was removed, keep the previous path, use a null line hash, and record `resolved` only after reviewing the removal and any replacement paths. Use the current scan ID and codebase-relative locations for the defect and relevant supporting evidence. The analysis should explain the relevant path, observed defenses and remaining uncertainty; provide a practical correction. Never place credential values, source excerpts or private data in findings. Location checks validate provenance, not the security conclusion.
6. Group repeated reports only when evidence shows one underlying defect and one correction. Keep separate risks that require distinct fixes. Summarize reviewed scope, tools, language coverage and gaps in the final report; an empty findings list is not a complete scan. Reassess findings when their source or reviewed revision changes.

Use language-specific details only when relevant: in Python, inspect decorators, imports and framework registration; in Rust, examine ownership, `unsafe`/FFI and synchronization, without assuming safe Rust has C memory semantics; in PHP, examine externally supplied request data, sessions and framework guards. For JavaScript/TypeScript, Go, Java and other languages, follow their actual routing, type and error-handling semantics. Configuration, scripts and other formats not represented in the index still need bounded direct inspection.
