# Research, evidence and verdicts

1. Run `vulnbell inbox --project <profile> --json`, then `vulnbell case <id> --project <profile> --json` for selected new/actionable cases.
2. Confirm the *exact monitored version or latest snapshot*, vendor/build, package ecosystem, aliases, upstream tag/commit and source assertion. An upstream issue rarely establishes applicability by itself.
3. Use the agent's browser/search tools for **public** news/advisories if allowed; start from the case's suggested queries. Date and cite claims. Register verified public links with `vulnbell case <id> --project <profile> --evidence-url <https-url> --json`; the CLI fetches and hashes the evidence as context except for the validated repository-advisory path described below. Never publish private paths or source. No search tool means mark web research unavailable, not scan failure.
4. Correlate fixes/backports against the relevant release tree and deployment context. If mapping or version is unknown, preserve that uncertainty.
5. Run `vulnbell impact <id> --project <profile>`. It returns the same five project-impact questions for every artifact. Obtain `vulnbell schema impact --json`, register a concise reviewed local note with `case --evidence-file`, and submit answers with `impact --from`. The saved result keeps the answers, rationales, evidence references, verdict, confidence, and open questions for JSON and Markdown reports. It does not change the case decision; record the verdict of step 9 for that.
   A lockfile or dependency declaration alone does not establish that an artifact was shipped or deployed. A sandbox result establishes behavior only for the tested inputs, not deployment. Use a reviewed artifact inventory or deployment record when available; otherwise leave deployment unknown.
6. When a workspace is available, inspect it statically first. Confirm the locked or built version, imports, configuration, feature flags, call sites, and whether relevant external input can reach the affected operation. Check that the dependency is compiled for the shipped target (not only a dev-dependency or another platform's dependency) and that the calling code is not test-only. Follow the call and data flow as deeply as the available code supports. Cite useful `path:line` locations in the reviewed evidence note, without copying secrets or the raw workspace into evidence storage.
   For a consequential finding, recheck the exact package and version, source-to-sink path and stated prerequisites against the cited evidence; actively look for a counterexample or a missing condition. Check that cited files and lines refer to the reviewed codebase revision. Record the precise unresolved fact and the next check; do not treat an empty search or schema-valid response as proof. A second reviewer is useful when available: give them the source claim and relevant evidence, ask them to challenge the result, and record their assessment separately. Do not delay a bounded review or claim independence that did not occur.
   For important local references, `vulnbell schema citations --json` describes the input for `vulnbell tools citations --project <profile> --case <id> --from <json>`. Supply explicit relative paths and one-based lines, with the zero-based codebase index from the case's `workspace_revisions`. An optional SHA-256 is of the UTF-8 line without its line ending. Exit 2 reports a missing, unavailable or mismatched line. This checks current references, not source meaning or runtime reachability; ignored files and non-Git trees are not bound by the Git fingerprint. Keep the review note and verify the cited conditions independently.
7. When no workspace is available, assess the authoritative report, affected source, fix, prerequisites, and exact software artifact in general terms. Answer project-only questions as `unknown`. State general impact and mitigation without claiming deployment or reachability in a particular project.
8. Before proposing a project test, verify that the real path, offline build, dependencies, toolchain, oracle and controls are feasible within current sandbox limits. `sandbox stage` accepts 1–1000 explicit files and an archive of at most 16 MiB; the guest is offline. Do not make an infeasible or elaborate full-project test routine pending work. For a serious unresolved upstream claim without adequate independent validation, a small synthetic `artifact_reproducer` using the exact checksummed dependency is appropriate only if practical and decision-relevant; its result does not prove the monitored project is affected. Reproducing a well-supported upstream issue is normally unnecessary. Otherwise document uncertainty, feasibility limits and human follow-up with `tools handoff`, without inventing a technical blocker; an explicitly required test remains pending or needs a genuine blocker. A test cannot establish deployment facts; leave them `unknown`. Before a needed test, present its script, oracle, control, inputs and limits together and wait for explicit authorization; run `sandbox prepare` first. Use checksummed inputs and never run third-party scripts on the host. See SKILL.md "Use the sandbox" for controls and blocker categories.
9. Obtain `vulnbell schema verdict --json` and submit `vulnbell triage <id> --project <profile> --from <file>`, referencing real evidence and existing IDs. Derive it from the impact verdict as SKILL.md step 8 describes: a `not_affected` or `mitigated` impact becomes `informational` with `applicability: not_affected`, never `actionable`.
   When a separate review is available, record it using `vulnbell schema challenge` and `vulnbell tools challenge --project <profile> --from <file>`. Copy the current case facts hash and the latest `impact_assessment` and `agent_verdict` evidence hashes; cite primary registered case evidence. The reviewer and relationship are self-reported. A disputed or inconclusive challenge makes the verdict non-current; reassess the objection and issue a new verdict citing the challenge evidence. A supported challenge does not close open impact questions or prove independence. Never send private code to an external reviewer without authorization.
10. Use *actionable* only when the impact assessment supports an update for this project; a version match or isolated reproduction alone does not establish project exposure. Use *review* for unresolved applicability; *informational* for evidenced non-actionable context; *dismissed* only with affirmative non-applicability evidence. Failure to reproduce is inconclusive.
11. Produce concise risk, confidence, affected instances, patch/mitigation if evidenced, source references and coverage limitations.
# Repository advisory evidence

For a case already linked to a GitHub repository advisory, `case --evidence-url` accepts its official `https://api.github.com/repos/<owner>/<repo>/security-advisories/<GHSA>` endpoint. The CLI promotes a published, non-withdrawn advisory to an affected claim only for case instances whose mapped repository, exact package and version range match. Other documents remain context. Reopen the case and rerun impact and triage after the facts change; a version match does not establish deployment, exposure or feature use.
