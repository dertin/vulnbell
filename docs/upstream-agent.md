# Upstream research

The local agent uses its own browser, search, and connectors to review GitHub issues and pull requests, GitLab issues and merge requests, Launchpad bugs and merge proposals, and related trackers. Rust stores inventory, times, known IDs, hashes, snapshots, cases, and import checks. The CLI does not scrape these sites. Its local screen only selects items for review; the agent decides every security claim that no structural rule settles. Advisory APIs are separate CLI integrations.

`vulnbell research --project vulnbell.yaml --json` returns a review window for each selected verified upstream. The first window defaults to 30 days, or uses `research.initial_since` or verified release dates when configured. After a complete review, the next window starts at that checkpoint with a five-minute overlap. A changed monitored context reopens the initial window. Scans can continue while the agent is unavailable without losing the unreviewed period. Seen events include IDs, content hashes and the agent's recorded assessment, so an unchanged item is not read again when its context is unchanged. New comments, code changes, or conditions can make a known issue worth reviewing again. Missing or partial research, including rate limits, does not advance the checkpoint. `research --reopen <upstream|all> --since <RFC3339>` moves completed checkpoints back when the screening method improves; seen events keep imported items from repeating unless `tools hits --recheck` is requested.

The agent screens titles, labels and bodies, not only titles marked “security.” Ordinary bug reports can describe attack conditions. For each security claim it records what the item itself states: cited advisory IDs, affected versions, where the fix is, the change carrying it and the required feature. The report shows those facts next to the case, and a not-applicable verdict for a fixed or other version requires the matching statement. It records unrelated items as seen, uncertain reports as hypotheses, and useful context as informational. Issues, proposed fixes, and news are not authoritative vulnerability reports. Stronger conclusions need evidence from the exact release, deployment context, public advisories, or a controlled lab test.

For the daily run, the agent fetches tracker responses with `gh` and `curl` into a run directory, and `vulnbell tools` processes them locally. The CLI still makes no tracker requests.

- `tools hits` reads the responses for every research target and lists any missing file with the exact request to make. It screens items on title, labels, body and closed issues, and skips items already imported with the same update time. It resolves cited advisory IDs through the GitHub advisory database, OSV and cve.org, and matches them against the inventory.
- `tools hits` settles structural items by rule: fix PRs whose closed issues carry the claim, repository advisories outside monitored versions, and identifier-only dependency updates or releases whose cited advisories are already covered. Other items go into a review packet.
- `tools draft` builds the research batch from those rules and the agent's decisions file (`schema decisions`). Copy each review item's `context_sha256` into its decision: a changed target context or item update requires a new assessment.
- `tools impact` and `tools triage` apply impact answers and verdicts for many cases from one file. `tools pending` lists what still blocks the report: open verifications, missing verdicts, open research windows and unfinished discovery.

The [workspace layout](../skills/vulnbell/references/workspace.md) gives the folder structure and command sequence.

The JSON import contract (`schema research`) checks the project, snapshot, upstream, instance IDs, and time window. It hashes observations, keeps history, skips unchanged records, and reopens meaningful changes. `complete` means **the agent reports** that it reviewed the full available window. The CLI cannot verify unseen website content. The Skill requires page coverage, event coverage, and evidence links. Private or inaccessible content remains a gap.

Code and bugs may be hosted on different sites. The agent must verify official links between them rather than infer identity from a name. Launchpad uses bugs and merge proposals. Its resource documentation defines available filters; `modified_since` is not supported on every operation.
